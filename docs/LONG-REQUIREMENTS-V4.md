# 长需求审阅与分段处理边界（v4）

问题：存储允许50000字符，单次生成限制20000字符。明确拒绝可避免静默丢失末尾，但用户还需要保留完整原文、核对分段条件，而不是删除证据来迁就模型。

## 已实现

追踪页面可打开“分段审阅完整原文”。服务端以当前或历史确认版本为来源，完整切分为最多4000 UTF-16字符的连续范围，保留所有换行、空白及末尾，避免拆开代理对。每段包含原文哈希、项目范围内的确定性标识、起止位置、涉及的稳定条目标识和跨段条目标识。同一原文在新版本中的逻辑条目标识保持稳定，版本ID仍独立；编辑文本或分段边界变化可能产生新标识，不能自动继承人工审核。

分段是确定性长度切分，不是语义拆解。人需要对照完整片段和相邻段，选择“接受为输入”或“需调整”，填写边界及依赖说明。当前实现记录这个判断，不自动重写原文或重分段；边界需要改变时仍须后续实现可审计的拆分方案编辑器。

迁移021新增审核与历史表，不更新已有需求/用例/证据。每段审核有独立revision，首次写入原子检查，后续写入比较旧revision；冲突409保留前端输入，不自动覆盖。项目锁和当前确认版本检查保证新版确认后不能再写旧版审核。历史审核可读，但新版本不继承“已接受”。API仍按登录账号核对项目权限。

## 已验证的处理与合并协议

`apps/api/src/trace/segments.ts`中的处理适配器只按人工已接受的分段顺序调用提供的处理器，一次一个；取消或失败保留已完成片段，不无限重试。单元验证使用受控处理器替身，未把模型连接接入生产生成。

合并检查分别核对缺段、重复/未知分段、原文哈希不一致、未知条目、每个片段中的条目遗漏、未人工接受的输入和未解决问题。特别是长单行跨越多个片段时，不能仅在第一段声明同一个条目标识，就假装其余片段都已处理。即使结构检查通过，语义完整性仍为`unverified`，`readyForAutomaticAdoption`恒为false。

真实数据库检查验证全文/末尾和位置、首次并发审核、修订冲突与历史、账号隔离、伪造片段/哈希拒绝及版本更新。浏览器检查读取失败、末尾原文、冲突保留输入、离开保护和保存后重读。报告路径见CONTINUATION-V4及最终验收报告；这些不代表长文本模型生成质量。

## 尚未完成及启用条件

1. 可编辑边界、显式跨段依赖图及原文范围完整性检查。
2. 有界模型工作队列、每段预算和可续跑结果持久化，与真实工具调用日志关联。
3. 分段输出合并后的全局依赖/矛盾/引用支持审查；不能靠“返回了全部ID”认证条件已理解。
4. 合成正常、末尾条件、重复条件、相互冲突和取消恢复案例的真实模型评测，经人工审核后再开放长需求生成。

因此v4仍保留超过20000字符的生成拒绝，没有增大上下文、截掉原文或把准备状态冒充已生成。分段审阅保存不触发任何模型收费调用。

## 迁移与恢复

先备份数据库，再按已有迁移入口应用020、021；不修改历史迁移。021是新增表/触发器，已存在业务不被改写。若需要回到v3代码，保留新增表及020令牌，不清空数据；记录新增审核在旧UI中不可见。恢复v4时继续读取这些记录。没有执行降级、删除表或覆盖备份。
