# 工序智伴约七分钟中文演讲稿

本稿对应v7实际功能，预计7分钟，包含页面操作停顿，最终时长以参赛者自行排练为准。只准备稿件，没有录屏、配音或视频。建议队员一主讲，队员二操作页面，队员三核对材料和时间；这是后续责任安排，不是既往贡献证明。

演示以原创“校园物品借用设计实训”为唯一案例，借期七日改为三日、禁止申请人自批、保留归还记录，均为合成约定，不是学校制度。完整网页验收用的是隔离账号、真实本地数据库和明确标识的模型协议替身；正式录制不得把替身生成说成真实模型。新13次真实模型响应可离线回放，只有额外获准的现场调用才能说“正在请求模型”。不需要为了讲稿再发起收费请求。

## 00:00—00:35 真实痛点

页面与操作：打开项目工作区，再打开预先准备的借用案例需求；鼠标指向“借用最多七日”和需求版本。合成数据为下方初始需求。预期画面：项目、需求原文和版本来源。

逐字稿：

各位评委老师好，我们的作品是工序智伴。我们关注软件工程实训里的一个具体问题：需求改了，学生以前做过的任务、测试和文档，还能不能作为现在的交付依据？比如校园物品借用，原来最多借七天，现在改成三天。旧测试即使通过，也不能直接证明新规则正确。我们希望让学生知道哪里需要重做，也让教师看到判断的依据。

备用讲法：若页面慢，指向已保存截图，说“这张是隔离环境的实际界面记录，下面解释它保存的版本关系”，不要说系统已经完成当前请求。

## 00:35—01:20 方案与角色

页面与操作：教师进入`/teaching`，展开“班级与任务发布”；打开七日要求的首版草稿，修改验收依据并保存，再点击“确认并发布任务”，看到已发布后再由学生领取。演示账号必须是已获授权教师；不要现场给真实账号提权。预期画面：同一任务修订、首版发布状态及班级进度。

逐字稿：

平台把需求、计划、测试和交付放在同一条工程流程里，也把学生和教师的职责分开。教师发布任务，学生领取后得到自己的私人项目。教师只能看到学生明确提交的固定快照，管理员也没有自动读取私人正文的权限。这里修改任务草稿，保存的是同一个任务；另一个窗口拿着旧版本保存，会提示冲突并保留输入。发布以后，要求就固定下来，后续修改必须产生新版本。

备用讲法：保存冲突时展示比较入口，说“我们先比较版本，不能直接覆盖另一窗口”；失败时保留输入，切到预先保存的任务版本截图，不重复点击创建。

## 01:20—02:20 学生确认与AI候选

页面与操作：学生`/classroom`加入合成班级，领取已发布任务后点击“打开项目与追踪”；`/projects/<id>/requirements`确认完整需求；`/projects/<id>/agent`展示已有候选及人工审核入口。采用已有合成记录或明确标识的协议验证记录，不现场默认点收费生成。预期画面：原文、候选任务、依据和未决项。

逐字稿：

学生先核对原文，再确认需求版本。AI可以帮忙整理计划，但不能替学生确认完整性。这里能看到实际的工具步骤、候选任务、验收方法和依据。学生需要检查：七日上限有没有遗漏，申请人能不能审批自己，什么输入会被拒绝。检查完再采纳，平台才保存正式待办。一个任务不一定不好，没有引用也不一定错误；关键是它能否解释覆盖了什么，以及还缺什么。这段网页流程记录使用的是协议替身，证明交互和状态链可以运行；真实模型回答我会在后面单独展示。

备用讲法：模型慢或失败时说“请求仍未完成，平台不会提前显示成功。这里改看保存的响应和状态”；不把回放说成现场生成，不重新请求凑演示。

## 02:20—03:35 需求变化与失效依据

页面与操作：教师从已发布任务“编辑或修订任务”→“创建修订草稿”，七日改三日，填写说明，选择向已有领取者提供建议，保存并发布。学生`/classroom`展开差异，填写处理说明并明确采纳；随后手动保存并确认三日需求，打开`/projects/<id>/documents`及`/projects/<id>/tests`。预期画面：所领v1与新v2、旧文档历史提示、当前用例与历史记录。

逐字稿：

现在把借期从七日改为三日。教师不能直接覆盖学生已经领取的要求，而是发布新版本，说明改了什么、影响谁。学生比较后，可以采纳，也可以说明为什么保留原版。注意，采纳任务新版不会悄悄改写学生自己的项目。学生还要手动更新并确认需求。接着，旧文档出现历史依据提示，旧版测试也不能算作当前版本通过。我们要补三日边界和超期拒绝条件，再检查禁止自批。平台把下一步工作指出来，但不会自动替人确认关联，也不会把有一条连线就当成验证完成。这是作品最希望讲清楚的价值：需求变化后，哪些证据需要重新建立。

备用讲法：若新版本尚未发布成功，停在原状态说明；使用同一次界面验收的第13—14页连续截图，不混接不同环境的版本作为一条真实链。

## 03:35—04:40 提交与教师反馈

页面与操作：学生“核对成果并提交”，明确共享固定快照；教师查看最新提交，人工起草、核对并发布反馈，退回；学生补“申请人审批自己的同一申请应被拒绝”的具体步骤，再提交。教师逐项核对并记录设计阶段例外理由。预期画面：两次提交、已发布反馈、验收理由，测试仍未执行或阻塞。

逐字稿：

学生主动提交以后，教师看到的是这一次的固定成果，而不是随时变化的私人草稿。老师指出，自批拒绝测试还缺少明确输入，发布反馈并退回。学生补上操作步骤，再次提交，第一次记录仍然保留。这里还有一个容易被忽略的区别：教师接受设计阶段成果，不等于全部测试通过。借用服务还没实现，我们就保留未执行和阻塞。教师检查需求、测试依据和版本一致性，有缺口仍验收时，必须写出具体的例外范围。AI点评也只能先成为草稿，教师确认后才能发布。

备用讲法：反馈未发布时学生看不到，是权限边界，不是演示故障。第二次提交若失败，保留输入和第一份快照，不重复声称已提交。

## 04:40—05:30 RAG与真实来源

页面与操作：打开知识库公共目录，显示51篇实际资料；选择校园借用案例“阅读原文片段”，核对版本和范围。只读目录与本地检索不请求收费聊天；不额外点击问答生成。预期画面：公共只读标识、已索引状态、可核对原文。

逐字稿：

知识库现在有五十一篇原创教学资料，覆盖八类软件工程主题和三个校园案例，使用五十三个本地向量片段。登录后大家共用公共资料，个人上传和作业仍然保持私有。这里能打开存储的原文，而不是只给一个看起来像引用的编号。找到资料只是第一步，还要判断它是否支持具体结论。召回命中不能说成回答准确率；资料不够时，我们要求明确说明缺口。目前课程仍需要独立教师审核，不把教学示例包装成学校制度。

备用讲法：索引服务不可用时直接打开已存原文，明确“这是原文阅读，当前检索不可用”，不要把关键词浏览称为语义检索成功。

## 05:30—06:25 真实AI验证与失败

页面与操作：本地打开`read-responses.html`和技术说明第16页，展示匿名响应、原始输入与失败记录。预期画面：保存的真实响应及待审表；绝不触发新请求。

逐字稿：

这是保存的真实模型响应，不是现场调用。早期十二次对照记录继续保留；另一次授权评测实际调用了九段长需求和四份教师点评。长需求的前八段通过结构校验，第九段的任务与条件关联不一致，系统暂停，后四段没有调用。我们保留原回答，也补上了可操作的错误提示，没有修改答案来制造成功。四份点评保存为草稿，仍待独立教师判断。结构正确、接口成功和回答质量是三件事。我们准备了匿名原文、条件、回答与空白审核表，保留错误和不可判断项，现在不声称质量提升了多少。

备用讲法：审核HTML打不开时用PDF第16页，说明原始回答仍在本地材料包；不能把AI辅助初审说成教师盲评。

页面与操作：回到追踪/交付缺口，再显示分层验证与团队责任页。预期画面：当前缺口和下一步，不展示虚构完成率。

逐字稿：

工序智伴帮助学生把“我做过”变成“我能说明依据”，让教师反馈落到具体版本和下一步。我们已完成分层测试和隔离环境的网页验证，真实教学效果仍需师生试用。团队将亲自复现流程、完成独立审核和材料核对，保留失败与未完成的记录，让AI成为可检查的工程助手。谢谢各位老师。

备用讲法：页面中断时直接完成口头总结，说明“当前操作中断，已有保存结果不受此口头展示影响”，不保证未确认请求已保存。
