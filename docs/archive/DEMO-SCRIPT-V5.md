# 工序智伴 v5 中文演讲稿（预计7分钟）

本轮仅准备稿件，未录屏、配音、剪辑或生成视频。以下时长是排练目标，不是实际成片检测结果；需由学生按本人语速排练。官方截图要求5—8分钟、MP4、至少1080p、普通话，字幕可选。旧v4视频不展示新增长规划，不能当成v5演示。

## 录制前的真实边界

贯穿场景为原创合成项目“设备借用实训演示”，不使用真实学生或业务数据。合成需求V1：普通学生提交借用申请；指导教师审批前检查库存；申请人不得审批自己的申请；审批失败保留原因并保持库存不变。V2追加：归还验收必须记录设备损伤，发现损伤时禁止直接归还入库。

流程演示可采用隔离回归环境的合成数据和模型协议替身，画面及口播须一直说明其范围。真实模型证据另打开审核包的`reviewer/read-responses.html`，展示v4已保存真实回答；它不是现场调用，也不是新长需求结果。不要直接在有真实计费配置的页面点击生成以排练。若后续自己决定现场调用，先另行配置授权范围并排练，不能沿用本轮授权。

准备两个合成项目：短需求完整流程、49,781字符长需求。长需求来自`evaluation/long-business-cases.mjs`，当前只有模型替身联调证据。短流程里的人工执行说明必须明确写“对照合成结果核对界面，非被测业务系统实际执行”；不把它登记成真正业务测试通过。展示真实通过时必须由操作者先实际执行相应受测系统并保存说明。本稿采用“未执行/阻塞”展示证据缺口，同样可以演示复核后交付。

## 0:00—0:40｜真实痛点（40秒）

页面：项目概览`/projects/<id>`。操作：展开当前确认需求与下一步；所需数据：上述V1。预期画面：已确认需求、任务和测试的真实计数，不要求全部完成。

逐字稿：

各位评委老师好，我们的作品是工序智伴，面向高职软件工程实训。我们关注一个具体问题：需求改了，任务、测试和交付材料却没有一起改。比如设备借用原本只要求老师审批，后来新增禁止申请人审批自己的申请。如果旧测试仍显示通过，学生就很容易误以为项目已经完成。工序智伴希望让每一步都有版本、有依据，也让缺口能够被看见。接下来使用的是原创合成场景，不包含真实学生资料。

## 0:40—1:20｜解决方案与需求确认（40秒）

页面：`/projects/<id>/requirements`。操作：读取完整V1→保存→确认最新版本→查看追踪条目。不要点击收费分析。预期：原文与确认版本一致，条目存在但不默认已验证。

逐字稿：

我们先把需求保存并确认。平台保留原文和版本，后续计划、测试和文档都带着自己的来源。这里的条目并不是完成勾选表：它用于说明一项要求被哪些任务处理、由哪些测试验证。模型建议的关联，需要人核对；确认有关联，也不代表测试已经通过。这样的区分，是为了让学生知道自己究竟完成了什么，还有什么需要补证据。

## 1:20—2:15｜计划生成与人工审核（55秒）

页面：`/projects/<id>/agent`。操作：打开已保存的合成运行→检查任务和验收方法→展开引用原文→查看人工审核→采纳已审核计划。所需数据：隔离协议替身已生成候选，画面标明“流程联调；模型替身”。预期：实际任务状态、工具记录，任务采纳后为待办。

逐字稿：

Agent会围绕确认需求组织计划，检索可用知识，并形成任务、验收方法和依赖。这里展示的是隔离环境的流程联调，模型响应是明确标识的测试替身；它证明状态与交互，不证明生成质量。我们可以逐项看任务是否遗漏禁止自审批这一条件，也可以打开实际提供的知识原文。一个引用编号存在，不代表它支持结论，所以仍然需要核对。审核通过后再采纳，平台才建立正式任务，而且任务仍是待开始，不会把生成出来的文字当成已经完成的开发。

## 2:15—3:10｜长需求保留与续跑（55秒）

页面：长需求合成项目的Agent页。操作：展开“完整原文·分段规划”→查看末段/原文位置→展示已保存作业片段与不确定状态→查看合并候选。不点击付费启动、重试或恢复。预期：完整49,781字符、方案修订、片段实际状态和审核项。

逐字稿：

长需求最危险的情况，是开头看起来处理成功，末尾条件却被截掉。现在平台保留完整原文、位置和哈希，先由人审核拆分方案，再逐段生成候选。跨段的单条要求会保留完整内容，合并时检查遗漏、重复和依赖。每段的尝试、原始输出和用量可以追查。网络超时后，我们不能确认提供方是否已经计费，所以不会自动反复调用，而是暂停等待核对。目前生产链路已经接通，并完成数据库和浏览器替身联调；新的长需求真实模型验证尚未执行，测试和文档的超长上下文也仍保留安全限制。

## 3:10—4:10｜测试与执行证据（60秒）

页面：`/projects/<id>/tests`，再到requirements下方追踪区。操作：查看当前版本用例→读取步骤/预期→填写真实的未执行或阻塞原因→查看来源修订→选择已有任务与用例关系→逐项核对。预期：缺口数来自数据库，人工状态有明确标识；可展示两个窗口冲突提示，但不强制现场复现。

逐字稿：

接下来是测试。每条用例说明前置条件、操作步骤和预期结果，并锁定需求与用例修订。平台不会直接执行学生上传的任意代码。这里我们没有运行真正的设备借用系统，因此保持未执行，或者登记无法执行的真实原因，不能为了演示把它改成通过。追踪区会告诉我们哪些条目缺任务、缺用例，哪些关联尚未人工确认。两个窗口同时登记时，后来的旧记录会被拒绝，原输入保留下来供比较，避免一条失败被另一窗口悄悄覆盖。这个环节让学生看到：测试文字、人工判断和执行证据，是三件不同的事。

## 4:10—5:05｜需求变更与交付（55秒）

页面：requirements→tests→`/delivery`。操作：保存V2并确认→观察当前版本缺口和历史提示→主动查看V1记录→登记变更关系→打开交付检查。预期：旧通过不计入V2；复核后交付仍显示未完成项，不假造全绿。

逐字稿：

现在我们新增归还损伤检查，确认第二版需求。旧任务和旧用例不会被删除，但它们不能替新要求作证。平台会指出哪些关系需要复核，旧版记录可以主动查看。我们先核对变更影响，再决定任务是否需要调整、用例是否需要重新执行、文档是否需要更新。交付检查使用相同的版本口径。即使还有缺口，也可以准确说明剩余工作，而不是导出一份看起来完整、实际没有依据的报告。我们希望学生学到的是如何交付可解释的结果，而不只是得到一份漂亮文档。

## 5:05—6:15｜AI价值与验证边界（70秒）

页面：离线`read-responses.html`及技术PDF的验证页。操作：展示正常、末尾条件、冲突资料三个样本，保留原回答及空白审核表。预期：12份真实回答、3条策略阻止、独立审核待完成；没有效果提升百分比。

逐字稿：

AI的价值，是帮助组织需求和工程候选，并把知识依据带进流程；系统的价值，是保存来源、约束状态，支持人检查和纠正。我们已经保存过十二次真实DeepSeek评测响应，现在展示的是当时原始响应的离线回放，不是现场重新调用，也不是刚才长需求的真实结果。我们保留了普通问答表现更好的样本：在末尾权限条件案例里，普通问答指出了禁止自审批，历史提示词回放却遗漏了它。不能只展示对自己有利的答案。接下来需要独立审核者判断遗漏、引用支持、拒答是否适当，以及实际修改量。HTTP成功、任务多、引用多都不能代替质量。因此目前我们不报告提升百分比，也不声称已经证明教学成效。

## 6:15—7:00｜总结与下一步（45秒）

页面：项目概览或技术PDF范围表。操作：停在真实下一步与能力边界；不要滚动大量统计。预期：清楚呈现需求变化后的验证闭环。

逐字稿：

工序智伴的核心，是让需求、任务、测试和交付证据在变化中仍能对得上。我们没有用自动确认替代人的审核，也没有把模型建议当成事实。当前已完成版本保护、任务规划、知识检索、人工测试记录和文档等流程，并补上了可恢复的长需求规划链路。仍待完成的是长需求真实模型质量验证、独立人工审核和实际师生试用。我们会按真实证据继续改进，让这个工具帮助学生理解软件工程的过程和责任。谢谢各位老师。

## 响应慢、失败或中断时的备用讲法

- 慢：“这里显示的是真实等待状态，没有预设完成百分比。为了不占用展示时间，我切换到已保存记录，并说明这不是新的现场结果。”
- 失败：“本次没有成功，系统保留输入和错误。模型调用结果不确定时不能盲目重试；我们先核对已有记录，再决定下一步。”
- 浏览器或API中断：“服务中断不会被标成任务完成。重启后的作业需要人工确认再继续；下面用保存的合成联调截图解释流程，它不代表实时执行。”
- 没有真实测试：“这条用例还没有实际运行，所以仍是未执行。平台揭示这个缺口，本身就是本次要展示的价值。”

操作提纲见`DEMO-OPERATIONS-V5.md`。正式录制前由演讲者核对页面文字、语速、数据范围和团队介绍；不能在口播中补造尚未实现的能力。
