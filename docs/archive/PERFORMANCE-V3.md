# v3 首屏资源与失败恢复验证

2026-11-01，本轮只拆分现有 Markdown 排版依赖，不增加运行依赖、页面或模型请求。原生编辑框、草稿状态和编辑保护仍在主入口中；排版模块按需加载。下载等待或失败时显示完整、由 React 转义的原文，用户可以继续编辑和复制；失败可单独重试排版，无需刷新丢失草稿。

## 功能与安全回归

三项新浏览器检查同时在开发服务与生产构建执行通过：

1. 首页不提前请求排版模块；故意挂起下载，末尾条件与随后输入保持完整；加载成功后文档大纲正确更新。
2. 故意中止排版资源下载，完整原文仍可读写；恢复网络并点“重试排版”后正常排版，新输入不丢失，未提交任何保存或模型请求。
3. A项目预览等待时切到B项目；迟到的排版资源只渲染B的原文，不将A内容写回B。

脚本和远程图片均不执行或加载；实际请求拦截记录与DOM断言共同核对。完整55组受控浏览器回归已通过，报告为`.runtime/reliability-ui-5cdd20db-eb51-4758-9ebe-3bae25984fa6/report.json`。这是受控HTTP验证，不是数据库或真实模型结论。

最初的基线采样曾误等隐藏的项目选择项，未获得有效时间；改为实际可见列表项后才记录上表。新增切项目测试第一次假设跨项目仍保留“预览”页签，实际组件因读详情重新挂载回到编辑模式；测试现明确打开B的预览，仍严格检查完整B正文及A不能回填。失败报告保留，没有把失败样本混入结果。

## 后续加载与响应边界

R23—R25把慢读取、错误响应和模块下载失败分开处理：普通GET最多等待15秒完整响应，成功状态损坏JSON不能继续当作有效项目；运行回看不以10秒刷新抢占尚未完成的读取。React按需模块导入失败保留邻近编辑器与侧栏，主动重新加载仍先核对未保存内容。

`pnpm verify:production-recovery`冻结当前dist并记录资源哈希，自建临时回环静态服务，复用同一组三项浏览器断言核对主/内层模块和需求侧栏的失败恢复。全部API为受控响应，不能冒充真实服务性能或收费模型验证。生产构建下载失败不等于已覆盖所有运行时组件异常。

## 复核方法

```sh
pnpm --filter @gongxu/web build
pnpm verify:web-entry
pnpm verify:reliability-ui --case=markdown_
```

`verify:web-entry` 自建临时回环静态服务，全部API受控，不读取`.env`或调用数据库/模型。`--label=名称 --dist=工作区内冻结的dist路径`可测指定旧产物。重新测量的时延可能不同，比较时必须控制机器、输入、浏览器、限速和运行条件。

生产失败恢复的复核：在web目录运行`node node_modules/vite/bin/vite.js preview --host 127.0.0.1 --port 5189 --strictPort`；另一个PowerShell终端在项目根设置`$env:SMOKE_WEB_URL='http://127.0.0.1:5189'`，运行`node scripts/reliability-browser.mjs --case=markdown_`。所有API均被测试拦截，不需要连接真实环境。测试完关闭自己启动的临时预览服务；不结束用户其他服务。
